# #6 監視・スキャン実行基盤

L1観測、L2/L3の定期実行、動的L9要求と子プロセス監視を実装する。
仕様の正本は[監視設計](monitoring-design.md)とIssue #1・#2・#3。
Incidentの自動検知・調査シーケンス・保持期限は[#7の実装](storage-incidents.md)、正式CLI・インストール・launchdの実装は[#8の運用手順](operations.md)を参照。初期実装時点の検証範囲と、後述の#38隔離検証の結果を区別する。

## 実行環境

- macOS、Python 3.11以上、標準ライブラリのみ。追加パッケージ不要。
- 開発確認は既存のPython 3.11.8から作成したプロジェクト専用venvで実施。
- Python 3.10を新たな対応対象に加える必要はなく、利用可能な3.11を最低対応版とした。
- pyenv/Homebrew/システムPython/グローバルパッケージ/PATH/シェル設定を変更しない。
- `diskutil`、`df`、`sysctl`はmacOS付属の読み取りコマンド。sudo不要。

既存の対応Pythonを明示指定して、リポジトリ直下でvenvを作成する。

```sh
/path/to/existing/python3.11 -m venv .venv
.venv/bin/python -m unittest discover -s tests -v
```

## 開発用ターミナル操作

以下は#6の検証用ハーネス。正式な配置とコマンド体系は[運用手順](operations.md)を参照。
データディレクトリは事前に作成し、初回だけ明示的に初期化する。以下の値は各ターミナルで同じものを指定する。

```sh
mkdir -m 700 /private/tmp/blackbox-demo-data
.venv/bin/python -m blackbox --data /private/tmp/blackbox-demo-data init
.venv/bin/python -m blackbox --data /private/tmp/blackbox-demo-data run
```

`run`だけではL1を毎分取得し、L2/L3の初期広域設定は読み込まない。
別ターミナルから、小さな検証用ディレクトリを明示して要求する。

```sh
.venv/bin/python -m blackbox --data /private/tmp/blackbox-demo-data scan L3 '/path/to/small-fixture/*'
.venv/bin/python -m blackbox --data /private/tmp/blackbox-demo-data status
.venv/bin/python -m blackbox --data /private/tmp/blackbox-demo-data cancel SCAN_ID
.venv/bin/python -m blackbox --data /private/tmp/blackbox-demo-data history --limit 20
.venv/bin/python -m blackbox --data /private/tmp/blackbox-demo-data results SCAN_ID
.venv/bin/python -m blackbox --data /private/tmp/blackbox-demo-data scan L9 '/path/to/small-fixture/*' --threshold 1048576 --max-depth 7
.venv/bin/python -m blackbox --data /private/tmp/blackbox-demo-data clear-waiting
```

出力はJSON。履歴中の`targets`・`options`・`metrics`はSQLiteに保存したJSON文字列。
`cancel`は指定したpending/runningスキャンの中止要求、`clear-waiting`は未実行のL9待機リスト全体の取り消し。
監視本体の通常終了は実行ターミナルのCtrl-CまたはSIGTERM。所有する子を中止・回収して終了する。
本体を止めても未実行の要求は残り、再起動後に実行する。

### 周期・対象の明示設定

Git管理外のローカルJSONを`run --config /path/to/local.json`で読み込める。
L2/L3の旧intervals値は互換性のため受理するが固定時刻を優先し、秒間隔の変更には使用しない。
起動時に1回読み込む。正式な設定統合・reloadは[運用手順](operations.md)を参照。L1の既定周期は60秒。L2は毎日7:00、L3は毎時10分（Macのローカル時刻）。

```json
{
  "intervals": {"L1": 60},
  "l1_path": "/System/Volumes/Data",
  "targets": {"L2": [], "L3": ["/path/to/small-fixture/*"]}
}
```

`conf_dirs`でL2/L3ごとのディレクトリも指定可能。各`*.conf`の空行・`#`コメントを除く行を対象に追加する。
同梱の`config/l2/conf.d/`（19指定）・`config/l3/conf.d/`（15指定）は設計済みの汎用初期対象。
**広域設定を有効化するとホームやLibrary等を再帰走査する。小規模検証では読み込まない。**

## 容量取得とマウント境界

- L2/L3/L9は対象選別に`stat`/`scandir`、再帰合計に標準`du`を使う。ファイル内容は開かない。L9は詳細範囲のPython列挙と、その下のdu一括集計を併用する。
- L2/L3/L9は割当容量（duの512バイトブロック数、直下ファイルは`st_blocks * 512`）。論理容量は取得せずNULL。旧履歴の論理容量列は保持する。
- ディレクトリ自身の容量も合計に含む。L2/L3/L9のハードリンクは各パスで計上する。L9はscan_version=2で旧方式（1）の重複排除と区切る。
- `~`を展開し、設定ルートは実パスへ正規化する。走査中のシンボリックリンクは追跡しない。
- 親子指定は1回の走査結果を共有。`/*`はglob展開せず、親合計と隠し項目を含む直下内訳を意味する。
- ルートごとに`df`からデバイスを取得し、`diskutil`の`Internal=true`を必須とする。明示指定した外部SSD/NASも拒否する。
- 配下のマウント点・異なる`st_dev`には降りない。明示された別の内部ボリュームは独立した走査ルートとして検証する（VMもこの扱い）。
- 選別時は`O_NOFOLLOW`で開きdevice/inodeを照合し、duは`-P`でリンクを追跡しない。マウント表を先に読み、深い境界へ至る枝も分割・除外する。L9の詳細列挙は親fdからメタデータを逐次取得する。
- `diskutil`を使用できない場合は走査を拒否する。収集できないパスを成功扱いしない。
- APFSの共有ブロック・clone・snapshot・圧縮等を厳密に配賦するものではない。L1とディレクトリ合計の一致は保証しない。
- 走査は同時点のスナップショットではない。走査中に変化するファイル、権限不足、深すぎる階層等は部分結果になり得る。

L9でもプレーンなパスは合計のみ。`/*`を指定すると同じ集計結果から直下を記録し、閾値の50%以上のディレクトリを最大7階層まで詳細出力する。
個別ファイルは閾値の5%以上、未満は親ごとの件数・平均割当容量を保存する。
容量合計の算出には配下全体のメタデータ走査が必要であり、7階層は詳細出力の上限。
同一実行内の詳細出力可能範囲を先に列挙し、その下の互いに重ならない部分木をduへまとめて渡す。下位結果を上位へ加算した後で容量閾値を適用するため、閾値未満の枝も最大詳細深度までは列挙する。明示された下位対象や深いマウント境界がある枝は、その位置まで分割する。
どの対象を深掘りするかというIncident側の判断・過去履歴比較は#7に接続する。

L2/L3の所属日は実際の開始日時に従う。待機中は開始日時を捏造しない。Storage Explorerの既存の日次代表選択（開始時刻、開始前は作成時刻）を維持し、過去日への補正・履歴の穴埋めは行わない。

## L2の取得範囲と対象外理由

本節は2026-11-04時点の[Issue #38](https://github.com/otanao1/mac-ssd-blackbox/issues/38)の調査・設計整理。対象追加やFDA対応の正式実装を行ったことを意味しない。現在の共通設定は`config/l2/conf.d/common.conf`の19指定で、ユーザーデータ・Library・アプリ・開発環境・一時領域・VM等を取得する。正確な実行対象は保存済みScanの`targets`を確認する。

### 領域ごとの扱い

| 領域 | 現在の扱い・方針 | 理由とIncident調査への影響 |
| --- | --- | --- |
| `/System/Library`等のOS本体、`/bin`、`/sbin` | 現行L2の初期対象外。日常変動の監視対象としては優先度が低く、対象外維持案 | 主にOSの配布・更新で変化する領域。日々不変という長期実測の結論ではない。OS更新に伴う増減は対象外の候補として残す。`/usr/*`と`/usr/local/*`は既存対象なので、OS関連領域すべてを対象外と読み替えない。 |
| `/dev` | 初期対象外を維持 | デバイス用の仮想領域で、通常ファイルの割当容量を集計してSSD使用量を説明する対象に適さない。 |
| `/System/Volumes/Preboot` | L2追加は保留 | duのパス別割当量とボリュームUsedの差が大きく、完全クローン以外にも未解明差が残る。低変動と確認したための除外ではない。OS更新等の変動候補として扱い、差を権限不足だけで説明しない。 |
| `/System/Volumes/Update` | 追加方針に合意済み。共通設定・本番設定とも未反映 | OS更新関連の一時利用がIncidentの増減候補となるため、変動の少ない対象として除外しない。追加の実装・配置・reloadは別の操作工程。 |
| `/System/Volumes/VM` | 既存の明示L2対象 | swap等の変動を調べる。新たに重複追加したり、DaisyDiskのSystem分類全体を未取得容量として加算しない。 |
| `/System/Volumes/Data`全体 | 全体ルートは現行19指定に含まれない | 現在の複数対象がData内の主要領域を取得する。全体を追加すると走査負荷・重複の整理が必要になる。19指定でData全域が網羅されるという意味ではない。 |
| 外部SSD/NAS・配下の別マウント | Scannerの既存安全条件で走査対象外 | 意図しない外部走査や別ボリュームの合算を防ぐ。内部の別ボリュームを明示対象にする場合は独立したルート検証が必要。容量安定性を根拠にした除外ではない。 |
| 権限不足のLibrary等 | 走査対象のまま。失敗を記録 | 容量変動の可能性があるため、権限エラーになったパスを一律に意図的な除外へ変更しない。 |

「設定にない対象」「マウント境界による`excluded`」「取得を試みた`error`／一部失敗の`partial`」を区別する。設定未指定の理由を既存の`excluded`へ混ぜない。`ignored`は未導入・保留であり、上表の説明だけでScannerの状態や親の`partial`判定を変更しない。

### 容量比較の限界

L1はボリューム側の空き容量・使用量、L2/L3はduによるパス別割当量である。L2の親子・重複対象を単純合算せず、マウント境界、権限不足、走査中の変化、APFSの共有ブロック・snapshot等を区別する。DaisyDiskの分類・GB表示・計測時刻とも一致を要求しない。

Prebootの既存調査ではハードリンクと完全クローンの重複が一部の差を説明したが、残差の原因は確定していない。完全クローン補正の広域調査は追加せず、既存du方式を維持する。ボリューム別Usedの履歴・可視化は#40で別検討とする。

## 権限比較の結果と確認範囲

[Issue #38](https://github.com/otanao1/mac-ssd-blackbox/issues/38)の代表例は`/Library/Bluetooth`と`~/Library/Mail`。個別ファイルの内容を調べたものではない。

| 条件 | 確認した取得差 | 根拠・限界 |
| --- | --- | --- |
| Terminal.app、sudoなし、同じduコマンド | FDA OFFではEPERM、ONでは両領域を取得 | ユーザーの実機報告。TerminalのFDAでlaunchd起動側も取得できるという意味ではない。 |
| DaisyDisk通常Scan、FDA ON | 両領域の容量・配下一覧を制限表示なく確認 | ユーザーの実画面報告。blackboxの全エラー領域との一対一比較ではない。 |
| launchd→Python→worker→duの限定検証 | 対象Python実体のFDA OFFで失敗、ONで両領域取得 | 同一経路で取得差を実測。過去にPythonへのFDA付与前後でエラー件数が変わらなかった観測は、正しい実行主体への適用を否定する根拠にはしない。当時改善しなかった原因自体は断定しない。 |
| Viewer同梱の専用ヘルパー、Python完全同梱 | ヘルパーFDA ONで両領域取得。同じ署名要件・配置先を維持した更新後も再承認なしで取得 | 隔離環境・開発署名での実測。共有Pythonへの恒久FDAを必要とせず、Hardened Runtime・ライブラリ検証を有効にした構成で確認。正式版・全OS・全配布方式の成立を保証しない。 |
| 過去のsudo比較 | 本整理で確認できる根拠からは、条件別・領域別の結果を十分に再構成できない | sudoを実施したという過去の会話と、比較結果を追跡可能な記録がそろうことを区別する。新たなsudo検証で埋め直さず、確認できない比較は未確定とする。 |
| DaisyDisk管理者Scan | #38の既存参考記録では、実施後も隠し領域が残る | 取得不能領域・共有容量等の内訳をすべて説明した記録ではなく、sudo実行のduと同じ挙動とみなさない。内部実装は推測で断定しない。 |

FDA、UNIXのアクセス権、sandbox等を混同せず、sudoだけですべてのプライバシー制限が解消するとは仮定しない。代表2領域での改善は、本番L2の権限エラー全件やL1/L2差の解消を示さない。取得不能な部分の容量は不明であり、差分全体を権限不足へ帰属させない。

現段階では権限エラー・`partial`の意味を維持し、専用ヘルパー同梱（案A）を第一候補とする。正式実装と再ログイン検証は後続の実装Issueへ引き継ぐ。Viewer/Widgetの既存ID・署名・App Group・DB読取責務を保ち、Viewer終了後も監視を独立継続する設計とする。今回の文書化は本番権限・設定変更の承認や実施を意味しない。

### 案Aの検証済み範囲と後続実装

案Aは既存Viewerに監視専用のネイティブヘルパーを同梱し、Pythonもヘルパー内にまとめる方式。現在の製品にヘルパーが組み込まれているという意味ではない。

- **隔離環境で確認済み**：launchdから専用ヘルパー・worker・duへ至る起動、代表2領域のFDA OFF/ON差、Python同梱・開発署名、同じ配置先・署名要件でのアプリ更新後の取得と同じ検証DBへの記録再開。ViewerをSIGTERMで終了した後も監視記録は継続した。無停止更新を確認したものではない。
- **ユーザーが確認済み**：正式版と別ID・App Groupの検証Viewer/Widgetで、合成データの容量値とグラフを実ホストに表示。正式Viewer/Widgetの構成での最終受入とは区別する。
- **未検証・後続の受入条件**：正式インストール/更新/復旧の実装、正式Viewer/Widgetの署名・App Groupを維持した組み込み、Viewerメニューからの通常終了、ログイン時自動起動・再ログイン/再起動後のFDA適用、配布方式や署名者・配置先が変わる場合、長期稼働、本番L2全体の改善率。現在のGUIセッションへの一時bootstrapを再ログイン実測の代わりにしない。

#38は調査・評価・設計方針の提示までとする。次の実装は後続Issueへ引き継ぎ、本書の追加だけでは実施しない。後続Issueの作成は文書PR確認後とする。

1. **UpdateのL2対象追加**：追加方針は合意済みだが、共通設定・本番設定とも未反映。設定変更・配布・reloadと必要な受入を別途扱う。Prebootは保留を維持する。
2. **案Aの正式実装**：同梱Pythonの再現可能なビルド・依存ライブラリの署名/ライセンス/更新、既存LaunchAgentとsetup/CLIの整合、二重起動防止、停止→アプリ置換→同じDBで再開する更新と復旧、FDA設定の案内を実装する。ViewerのDB読み取り専用とWidgetの表示キャッシュ責務を維持する。Viewer終了後の監視継続と、Viewer終了後に表示キャッシュ更新が止まる既存仕様を混同しない。上記の未検証事項、とくに再ログイン検証を受入へ含める。

## 排他・待機・復旧

- `monitor.lock`で監視本体を1つに制限する。`scan.lock`を子へ継承し、L2/L3/L9は同時に1本。
- 監視本体が異常終了しても生存する子がロックを保持する。再起動した本体はその終了を待つ。
- 定期L2/L3も既存pendingに保存し、競合では待機する。同じレイヤーの定期pendingがある場合のみ次の定期要求をskippedにする。実行中の定期Scanがあっても次周期のpendingは1件保持できる。
- L9待機要求を先に実行し、その他はIncident・manual・periodicを区別せず作成順。実行中のScanは新しい要求で中断しない。新しいキュー・管理表は追加しない。
- L1は従来どおり既定60秒間隔。L2は毎日7:00、L3は毎時10分（Macのローカル時刻）。次回予定を永続化し、開始・終了や待機遅延ではずらさない。
- 初回は次の固定時刻を登録する。永続化済み予定をスリープ・停止中に超過した場合、復帰後に各レイヤー1要求を処理して次の固定時刻へ進む。過去の周期を連続再実行しない。旧秒間隔の未来期限は次の固定時刻へ移行し、期限超過分は1回処理する。
- 定期要求と次回予定を同一トランザクションで保存する。保存障害時は予定だけ先へ進めない。再起動後もpendingを保持する。
- 手動L2/L3は同一レイヤー・正規化済み対象集合が同じrunning/pendingを再利用し、JSONにsuppressed=trueを返す。オプションを変えても重複実行しない。完了・失敗・中止後は再実行できる。
- インストール済みCLIの `periodic-l2` は読み込み済み定期L2対象と既定オプションでtrigger=periodicを登録する。同じ定期L2がrunning/pendingなら追加せず既存IDを返す。次回予定は変更しない。
- L9はパスと取得内容（閾値・最大深度）の組で重複排除。実行開始時に待機対象をトランザクションで実行履歴へ移す。
- 実行リストは変更せず、新しい要求は次回用待機へ追加。同じパス・内容のrunning/succeeded/partialは開始後30分間再取得を抑止する。
- APIの`request(..., cooldown=...)`で抑止時間を変更可能。失敗・中止は再取得を妨げない。
- 中止要求は通常約0.2秒間隔で確認。応答しない所有子へ5秒後SIGTERM、10秒後SIGKILLを送る。
- 子が結果を確定せず終了した場合はfailed（中止要求済みはcancelled）。再起動後はロック解放を確認して残存runningを確定する。
- 旧本体の生存子についてはDBの中止要求で停止できるが、新本体はそのPIDへ強制シグナルを送らない。

## 保存・状態と後続Issueの接続点

既存の保存ディレクトリに`blackbox.sqlite3`を作成する。DBはmode 0600、保存ディレクトリは0700を推奨。
設定・データはGit管理外。以下は#6時点の基本表。#7で[集約・期限削除・Incident表](storage-incidents.md)を追加した。独自容量上限は設けない。

| 物理構造 | 用途 |
| --- | --- |
| `scans` | scan ID、層、契機、対象JSON、取得オプション、状態、時刻、PID、進捗、中止要求、エラー、負荷測定 |
| `results` | scan ID・パス・種別ごとの容量、論理容量、成功/失敗、少量ファイルの統計 |
| `l1` | 観測時刻、総量・使用量・空き量・一般ユーザーの利用可能量、起動ID、エラー |
| `waiting` | L9の動的な待機パス・取得オプション・要求時刻 |
| `meta` | 次回定期実行期限 |

走査結果は設計の2論理構造（履歴・測定結果）で表現し、永続的な「スキャン対象」専用構造は設けない。
L2/L3/L9は必要な集計結果だけを保持し、全ノードTEMP表を作らない。L9はディレクトリ集計・保存候補・失敗証跡と小ファイル統計のみを保持し、小ファイル個々の情報は保持しない。結果は最大100行ずつ短いトランザクションで保存し、走査・du待機中に書き込みトランザクションを保持しない。大量の全履歴を監視本体のメモリへ読み込まない。
対象パス失敗も測定結果へ保存する。最終状態はsucceeded/partial/failed/cancelled/skipped。
走査中はcurrentに現在対象、completed/totalに指定対象の結果確定数を保存する。
ディレクトリ内の総項目数は事前走査せず、進捗率は算出しない。中止・失敗時の結果は取得済み部分のみ。

保存先のdevice/inode変更・書き込み失敗は通知して記録を停止し、同じ保存先が復旧すれば再試行する。
通常の再オープンはSQLiteの`mode=rw`を使い、マウント消失時に新しいDBを自動作成しない。
意図した保存先の初回検証・永続的なマウント識別・復旧は[#8の保存先設定](operations.md)で実装した。
初回`init`は利用者が意図したマウントを確認してから行う。

接続点は`runtime.Monitor.tick()/close()`、`runtime.request()`、`runtime.observe()`、`store.Store`。
#7ではscan IDをIncidentから参照し、履歴比較・保持処理を追加できる。
#8の正式CLI・設定・launchd操作はこれらのAPIへ接続する。

## #18 L9合成比較と競合検証

`.venv/bin/python -B tools/verify_l9_du.py`で、浅い50ディレクトリ×100ファイルと、深さ10の10枝×500ファイル（各5,000ファイル、90%空ファイル）を比較した。閾値64KiB、最大詳細深度7。旧方式と新方式を各3回、別プロセス・実行順交互で計測し、以下は中央値。割当容量・保存結果数は全回一致（浅い601行、深い71行）。Python 3.11.8 / macOS、標準ライブラリのみ。

| 形状・方式 | 経過秒 | CPU秒（終了済み子を含む） | worker最大RSS | TEMPノード書き込み | プロセス帰属書き込み |
| --- | ---: | ---: | ---: | ---: | ---: |
| 浅い・旧 | 0.258 | 0.255 | 29.1MiB | 5,051行 | 328KiB |
| 浅い・新 | 0.222 | 0.219 | 27.7MiB | 0行 | 1,028KiB |
| 深い・旧 | 0.450 | 0.449 | 29.4MiB | 5,101行 | 256KiB |
| 深い・新 | 0.094 | 0.046 | 27.0MiB | 0行 | 216KiB |

新方式の終了済み子の最大RSSは約2.9MiB（worker値と同時ピークの合計ではない）。TEMPページ数は旧335/425ページ、新0ページ。トレースのBEGIN→COMMIT到達の最大区間は旧約200ms、新約0.7〜0.9ms。これはCOMMIT完了までの時間・厳密なロック保持時間ではない。新方式の結果保存は最大100行で、区間内に走査・du待機を含めない。

浅い木ではPython列挙が残り、短いCOMMITの増加で書き込み量は増えた。全形状の高速化・総書き込み削減は保証しない。小規模・キャッシュの効いた合成データで、SQLトレースの計測負荷を含む。I/Oはworker帰属値であり、du子のI/O・装置全体の転送量ではない。

同じ2形状をまとめた実workerによるL9を3回実行し、すべてversion=2/succeeded。L1相当の合成観測26件（worker実行中24件）、別接続による読み取りと短い書き込み202回、SQLiteエラー・Scanエラー・監視中断0件、DB整合性ok。内部ディスク判定は合成fixtureのst_devへ差し替え、実du・マウント境界処理・worker・排他・結果保存は通常処理を使用した。実L1の空き容量観測・本番設定・launchd・長時間運用の試験ではない。

自動テストでは、合成SQLiteの強制BUSY・バッチ挿入失敗時のrollback/failed確定・ロック解放、取得途中の失敗/中止時の証跡保持、du子の終了回収も確認する。通常の短い競合でエラーが出なかったことは、長いロック保持やすべてのdatabase is lockedを解消した保証ではない。
