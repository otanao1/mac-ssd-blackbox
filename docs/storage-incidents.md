# #7 保存・保持・Incidentライフサイクル

Issue #1・#2・#3・#6・#7と[監視設計](monitoring-design.md)に基づく。
Python 3.11以上・標準ライブラリ・既存SQLiteを使用する。Scanの走査・排他・待機構造は維持する。
正式CLI、設定の配布/reload、launchd、インストーラー、起動時の永続的な保存先識別は[#8の運用手順](operations.md)を参照。

## 保存形式と保持

既存の`blackbox.sqlite3`へ`l3_daily`と`incidents`を追加する。
既存DBは通常のStoreオープンで追加テーブルを作成する。既存履歴は再初期化しない。

| データ | デフォルト | 期限の基準 |
| --- | --- | --- |
| L1 | 非集約で3暦年 | 観測時刻 |
| L2 | 非集約で3暦年 | 開始時刻、未開始は作成時刻 |
| L3生履歴 | 30日経過後に日次集約 | 同上 |
| L3集約 | 3暦年 | UTC集約区間の終了 |
| L9 | 非集約で3暦年 | 開始時刻、未開始は作成時刻 |
| Incident | 通常履歴から独立して3暦年 | 検知時刻 |

3暦年前の同日時を期限とし、2月29日は2月28日に補正する。生データは期限と同時刻なら残す。集約区間は終了時刻が期限以下なら削除する。
L9の通常履歴も独自容量上限を設けず3年で削除する。Incidentへ必要な抜粋を残す。
実行中・未処理のスキャンは削除しない。調査中の関連scan IDも評価を保存するまで保護し、
同じL3集約区間全体を一時的に延期する。Incident期限後はこの保護も終了する。

Monitor起動時と以後24時間ごとに`retention.maintain()`を実行し、期限を`meta`に永続化する。
停止中の定期処理を連続実行しない。保管データ全体のメモリ展開は行わない。
集約・元結果/scan履歴削除・Incident期限削除は同一SQLiteトランザクションで行う。
失敗時はロールバックし、復旧後に再試行する。スキャン子とSQLiteの通常のトランザクション排他を共有する。
削除はSQL DELETEで、空きページを再利用する。毎回のVACUUMやDBファイル縮小、独自の保存容量上限は導入しない。

### L3集約

UTC 00:00起点の1日・パス・結果種別ごとにJSON評価を保存する。
30日を過ぎた観測を含む**区間全体**が期限を迎えてから処理するため、生履歴は通常30〜31日残る。
区間内の各測定について以下を残す。

- 測定数、正常数、取得失敗数
- 正常観測の開始/終了時刻・開始/終了割当バイト数
- 最小/最大/平均割当バイト数、合計（平均の検証用）
- 区間内の隣接する正常観測間の最大増加量・最大減少量

平均は時間加重ではなく正常測定の算術平均。失敗・部分取得の容量を0として扱わない。
変化量は失敗観測を飛ばした正常値同士の差で、同時点のスナップショットではない。
日付境界の変化は隣接日の終了/開始値から追跡できる。L3はディレクトリ容量なので、
空き容量の急減に対応する**増加量**も残す。L1の空き容量自体は毎分データで保持する。
欠損パス・設定から除外されたパスは補間しない。skippedなど測定結果のない実行は容量標本を生成しない。

## Incident検知と調査

L1の`free`を用い、`available`は検知情報内の参考値として残す。
初回の正常観測は基準の確立に使い、以前の正常観測がある場合に判定する。
エラー観測は判定しない。検知済みL1時刻とIncident/L3要求を一緒にコミットして重複を防ぐ。
再起動時は未判定のL1を古い順に処理する。#6から移行した初回だけは最新観測から開始し、過去全履歴のIncidentを生成しない。

| 検知条件 | 判定期間 | 判定の実行間隔 | 閾値（初期値） | 比較方法 |
| --- | --- | --- | --- | --- |
| `DROP_SPACE_1m` | 1分間 | 1分ごと | 1GiB以上減少 | 直前の正常なL1観測と現在を比較 |
| `DROP_SPACE_24h` | 24時間 | 24時間ごと（1日1回） | 5GiB以上減少 | 前回の24時間判定時点の空き容量と現在を比較 |

- `DROP_SPACE_1m`は毎分L1を処理する際に判定する。毎分収集の遅延を考慮し、
  前回から90秒以内の観測を実際の経過秒数で1分換算し、長い停止を1分減少とみなさない。
- `DROP_SPACE_24h`は最初に処理した正常観測を比較基準とし、その24時間後以降の
  最初の正常観測で1回だけ判定する。過去最大値やIncidentの検知時刻は比較に使用しない。
  検知の有無にかかわらず、実際の判定観測を次の基準とし、そこから24時間後を次回期限とする。
  `meta`の`drop_space_24h:<L1対象パス>`に基準観測（時刻・空き容量等）と`next_due`をJSON保存する。
  基準観測の時刻が前回判定時刻であり、監視対象ごとに独立して再起動後も引き継ぐ。
  エラー/欠測では更新しない。期限後の正常観測が遅れた場合は実測端点を比較し、
  実経過時間を記録する。値の補間や欠落期限の連続実行は行わない。
- 一方の検知やIncident作成がもう一方の判定基準・期限を変更することはない。
  24時間状態、判定済みL1時刻、Incidentと調査要求は同じトランザクションで保存する。
  保存失敗時はすべてロールバックして再試行する。
- IncidentTypeは`DROP_SPACE`のまま、`detection.rules[].rule`に`DROP_SPACE_1m` /
  `DROP_SPACE_24h`を記録する。同一観測で両条件が成立したら1件に両条件を残し、調査を重複実行しない。
  既存Incidentの旧`minute` / `day`記録は書き換えない。旧版から更新後の24時間状態がない場合は、
  次に処理する正常なL1観測から基準を確立し、推測による過去判定は行わない。
- `LOW_SPACE`：以前の正常観測で5GiB超、現在5GiB以下への突入。低いままでは再作成しない。
- `REBOOT`：同じL1対象の以前/現在の正常観測で、空でない起動IDが変化。
  再起動前最後と再起動後最初の記録を残す。再起動直前の取得は保証しない。

異なる観測でそれぞれの条件が成立したDROPは別Incidentとする。Severityや自動統合は追加しない。
以下の順で調査し、既存スキャンを中断せず、既存の相互排他と子プロセス実行を利用する。

1. L3を追加取得し、検知以前に完了した同層の最新succeeded/partialスキャンと比較する。
2. 比較可能な正常パスの割当容量増加が検知閾値の50%以上なら原因候補とする。
   基準がない/パス種別が違う/取得失敗の値を増加とみなさない。親子の増加量を合算しない。
3. L3で候補がなければ同じ方法でL2を追加取得。L2でも候補がなければ`unidentified`で終了して通知する。
4. 候補ディレクトリを`/*`でL9へ渡す。ファイル候補は親ディレクトリを調査する。
   待機の集約・30分再取得抑止は既存`request()`を利用し、共有/抑止されたスキャンにもscan IDを記録する。
5. L9が終わるまで`investigating`を維持する。最大7階層、閾値50%のディレクトリ深掘り、5%の個別ファイル基準は#6のまま。
   同じ対象・取得内容の過去L9が残っていれば比較可能な差も保存する。基準がなければ現在容量を証跡にする。

L9用の検知閾値は成立したDROPルールの値（両方なら短期値）、LOWは低容量閾値、
容量差のルールを持たないREBOOTは短期DROP閾値を使用する。

L9スキャンの成否と、容量増加箇所の特定を分けて評価する。
L2/L3の0.5T以上という条件は調査候補の抽出に維持し、最終判定は**L9自身の差分が1箇所でT以上**の場合とする。
TはIncidentの既存の検知閾値で、新しい数値閾値は追加しない。

| 対象別の評価理由 | 条件 |
| --- | --- |
| `growth_identified` | 同じパス・種別の正常なL9差分で、ファイルまたはディレクトリにT以上の増加を確認 |
| `no_baseline` | 正常取得できたが、比較可能な過去L9がない |
| `insufficient_evidence` | 正常なL9比較ができたが、1箇所でT以上の増加がない |
| `scan_incomplete` | T以上の正常な差分を確認できず、対象/比較元が取得不完全・失敗・中止等 |

比較元は、現在のL9開始前に完了した同じ対象パス・取得条件（閾値・最大深度）のうち、
正常値同士で比較できるパスがある最新のL9を選ぶ。新しい試行に比較可能なパスがなくても、以前の比較元を利用できる。
比較可能な過去L9がない場合、同条件の不完全な試行が残っていればそのID・状態も保存する。
その場合も両スキャンに正常値がある個別パスは比較できる。T以上の正常な差分を確認できなければ
`scan_incomplete`とし、比較元そのものがない場合の`no_baseline`と区別する。
過去に記録のないファイル等は0扱いせず、双方に同じパス・種別の正常値があるものだけ比較する。

複数対象を含むスキャンは、対象ルート自身とパス区切りで区切った配下に結果を限定して評価する。
全体状態が`partial`でも、対象ルートの容量が正常で、その配下に取得失敗がなければ、その対象は正常取得として扱う。
スキャン全体の状態と対象の取得完全性は別途保持し、他の対象の失敗を正常扱いしない。
対象内に部分失敗があっても、比較前後とも正常に取得できた個別パスでT以上の差分があれば特定を認める。
その場合も失敗箇所と取得不完全の情報は残す。`failed` / `cancelled`等の実行は特定根拠にしない。

全対象の実行・待機が解決するまで`investigating`を維持する。解決後は、**いずれかの対象で**
`growth_identified`ならIncidentを`identified`とする。他の対象が`no_baseline`や`scan_incomplete`でも妨げない。
1箇所も確認できなければ`unidentified`。理由が混在する場合も対象別の理由をすべて残し、
全体の代表理由は`scan_incomplete`、`no_baseline`、`insufficient_evidence`の順で選ぶ。

ディレクトリ単位（対象ルートも含む）の特定を認め、`kind`でファイル単位かディレクトリ単位かを識別する。
親・子や複数対象の差分は合算しない。例えばT=1GiBで親+0.75GiB・子+0.75GiBでも特定条件を満たさない。
T以上のパスはそれぞれの差分で記録し、増加量の合計値は作らない。
過去L9がなくても、現在のディレクトリ容量・大きなファイル等の証跡は保存する。
アプリ内部の根本原因やL1減少との厳密な因果関係は保証しない。
状態3種類、最大7階層の取得方式は維持し、L9の追加自動実行・新しいテーブルは導入しない。
完了済みIncidentの自動再評価・過去JSONの書き換えは行わず、調査中の次回評価から新方式を使用する。

## 独立した証跡とAPI

`incidents`の1行に検知条件とL1前後値、容量差の評価、原因候補、調査段階、
比較元/調査scan ID配列、状態、更新時刻、メモを保存する。専用の関連付けテーブルや外部キーは設けない。
各調査段階には実行時刻・対象・取得内容・状態・エラー、比較可能な変化件数と
絶対変化量上位20件、失敗件数と抜粋20件を保存する。
L9の`investigation`内には、`scans`にスキャン自体の状態・エラー・時刻・対象・取得条件を、
`target_evaluations`に対象別の比較元ID、取得完全性、比較元の有無、比較件数、差分評価・理由、
対象内の容量上位20件、比較元の失敗抜粋20件を保存する。
判定に使った`findings`には、対象・パス・種別・前後容量・増加量・取得scan ID・比較元scan IDを残す。
Incident全体の`evaluation`にも全体理由・対象別理由の一覧・確認したfindingsを保存する。
原因候補とT以上のfindingsは別途保存し、差分上位20件の制限で落とさない。
生履歴全体を複製しない。scan IDは通常履歴削除後も証跡の出自として残り、
評価値・抜粋はIncident行だけで参照できる。

#8のCLIからも利用するPython API：

```python
from blackbox.store import Store
from blackbox.incidents import details, note

store = Store('/path/to/existing/private-data')
try:
    recent = details(store, limit=20)          # JSONへ変換可能な辞書の一覧
    incident = details(store, 'INCIDENT_ID')   # 0件または1件
    note(store, 'INCIDENT_ID', '調査メモ')     # メモ全文の置き換え
    summaries = store.rows('SELECT * FROM l3_daily ORDER BY bucket DESC LIMIT 20')
finally:
    store.close()
```

## 設定と保存先障害

既存の開発ハーネス`run --config`のローカルJSONへ、必要なキーだけ追加できる。
Monitorの`retention=`・`incident_thresholds=`引数でも同じ部分上書きが可能。
値は正の整数（cooldownのみ正の実数も可）。未知のキーや無効値は起動時に拒否する。

```json
{
  "retention": {
    "l1_years": 3, "l2_years": 3, "l3_years": 3, "l9_years": 3,
    "incident_years": 3, "l3_raw_days": 30, "l3_bucket_seconds": 86400
  },
  "incident_thresholds": {
    "drop_minute": 1073741824, "drop_day": 5368709120,
    "low_space": 5368709120, "l9_cooldown": 1800
  }
}
```

`l3_bucket_seconds`は集約粒度。変更前の集約は元のwidthで残し、再集約しない。
保存先のdevice/inode確認を維持し、DB自体のdevice/inode変更・シンボリックリンク置換も拒否する。
書き込み障害時はtick処理を停止し、所有スキャン子には終了を要求する。
Monitorの`notify(event)`へ`recording_stopped`を一度通知し、復旧を再試行する。
元のディレクトリとDBのidentityが戻り、`mode=rw`で再接続・書き込み確認が成功した後、
`recording_resumed`を一度通知する。自動mkdir・DB再作成・別保存先への切替は行わない。
`recording_error`で停止理由を確認できる。デフォルト通知先はstderrのJSON。
調査終了も`incident_completed`として通知する。

初回保存先検証と再起動をまたぐマウント識別は[#8](operations.md)で追加した。
通知は既存JSONイベントとCLI状態表示を利用する。SQLite TEMPの内蔵SSD書き込みは許容し、外付け配置を必須としない。
測定用のtemp_store_directory設定は製品へ導入しない（[元の引き継ぎ](https://github.com/otanao1/mac-ssd-blackbox/issues/8#issuecomment-6354212132)）。
今回の保存先置換/書き込み不可/復旧検証は合成ディレクトリと注入エラーによるもので、実SSD/NASの切断試験は行わない。

## 検証

```sh
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python -m tools.benchmark_lifecycle
/usr/bin/time -l .venv/bin/python -m tools.benchmark
```

保持境界・うるう年・集約の極値/急変/失敗数・冪等性・トランザクション失敗、検知3種、
LOW再突入、L3→L2→L9、状態遷移、共有L9・抑止と過去比較、調査再開、通常履歴削除後の証跡、
保存先/DB置換、書き込み障害・復旧通知、実子の段階的調査を自動テストする。
DROPの独立した判定間隔、120分横ばい、24時間の端点比較、再起動・欠測・トランザクション失敗、
同時成立時の調査非重複も検証する。
L9は過去なし、同条件比較、T未満/同値/超過、ファイル/ディレクトリ、親子や複数対象の非合算、
複数対象の分離、共有partialスキャン、一部比較元欠落/取得失敗、証跡期限の独立性も検証する。
時刻とデータは合成し、3年待機や既存監視データの操作を行わない。
