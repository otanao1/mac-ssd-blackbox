# Issueの作成・更新・結果記録

[開発ルール](../../../.claude/rules/development.md)に従う。対象repositoryとIssueを確認し、本文を先に読み、リンクされた根拠や必要なコメントを追加で読む。

## 作成

- Open/Closedの既存Issueから重複を確認する。目的、現状、合意範囲、完了条件、対象外、関連先と理由を記す。
- ラベル・タイトルはblackboxの既存運用に合わせる。BodyMapのラベル・動画ID・Previewの規則や新しい分類機構を導入しない。
- 不可逆なデータ変更・安全条件の変更等、追加の設計判断は結果を明示して相談する。

## 本文を安全に更新する

1. 合意済みの変更と許可範囲を確認する。未承認の範囲変更は差分を提示し、返信を待つ。既に具体的な更新指示を得ている場合は再承認を求めない。
2. 更新直前の本文と更新日時を取得し、元本文をGit管理外に保存する。秘密を含む記録は公開しない。
3. 変更箇所だけ更新する。プログラムで置換する場合は期待した件数をassertする。空本文・意図しない大幅短縮・履歴や完了条件の消失を防ぎ、送信前に差分を確認する。
4. 送信直前に再取得して他者の編集が入っていないか照合する。不一致なら再適用して差分を見直し、古い本文で上書きしない。API更新は原子的な排他ではない点に注意する。
5. コネクタの構造化引数または`gh issue edit --body-file`で送信し、直後に再取得して意図した差分のみか確認する。失敗時に空本文で再送しない。

本文は現在の合意・状態を分かる形に保ち、経緯や生ログの複製は避けてコメントへのリンクで根拠を示す。対象外・別Issueへの引き継ぎを無断で完了条件に戻さない。

## 結果の記録

- 完了条件ごとに、変更・検証コマンドと結果・根拠・未対応を対応付ける。
- 今回AIが確認したこと、過去の検証記録、ユーザーの別セッション報告、合成データ、実機・実画面、未確認を区別する。未再実行のテストを成功と書かない。
- PR前にREADME・関連docs・Viewer利用ガイドと実装の差異を確認し、必要な更新は同じPRに含める。更新不要も理由を示す。
- 公開記録では実DB・生ログ・端末固有パス・署名情報を除く。記録の許可がない場合は案を用意して提示し、無断投稿しない。
- IssueをCloseせず、終了判断時は[Close確認](../closing-issue-check/SKILL.md)へ進む。
