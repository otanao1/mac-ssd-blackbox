# mac-ssd-blackboxのIssueクローズ前の確認・後片付け

## 役割

このSkillの目的は、単なるチェックリストを生成することではない。

Issueをクローズしようとする段階で、クローズ前に確認すべき事項を漏れなく確認し、未対応事項があれば明示して必要な対応を進めるために使う。実行できる対応は対象プロジェクトの`AGENTS.md`・`CLAUDE.md`等の指示、利用可能な安全ガード・開発フローに従って行い、新しい権限やルールは定義しない。

対象Issueの本文と合意済みコメントを正本とする。このSkillはmac-ssd-blackbox内で管理し、共通Skillの導入・配布・同期や他Skillへの依存を前提としない。

Issueの機能的・ビジネス的な完了判断、およびIssueのクローズ判断はユーザーが行う。PRのMerge承認、機能受入、Issue単独のClose承認は別々に扱う。PR本文を扱う場合は`Related to #N`を使い、Issueを自動Closeする記法を入れない。

## 発動条件

以下の**いずれか**に該当した場合に発動する。これらは**OR条件であり、複数条件を同時に満たす必要はない**。

- Issueに記載された作業・完了条件が完了し、クローズできそうと判断したとき
- 作業が終わったと判断し、Issue終了の流れに入ったとき
- ユーザーに「クローズしてよいか」「クローズしていい？」等を確認しようとするとき
- ユーザーから本番・実機確認の完了を報告されたとき
- ユーザーから「残件はない？」「後片付けは？」「終わった？」等、完了状態・後片付けについて尋ねられたとき
- PRのMerge後など、Issueをクローズする段階に入ったと判断したとき

本番・実機確認の完了は本Skillの必須前提ではない。確認そのものは対象プロジェクトの手順に従い、本Skillでは必要な確認の結果と未確認範囲が記録されているかを確認する。別Skillの導入は前提にしない。

## 確認・対応範囲

対象Issueについて、次を確認する。

PR・Merge・branch・stash等の状態は、会話中に以前確認した結果ではなく、その場でGitHubの読み取りツール（利用可能なコネクタや`gh`）・`git`から取得した最新の結果で判断する。サブエージェント等の「完了」報告も同様に確かめ直す。

1. **Issue状態**
   - 完了条件が実態に合わせて更新されているか
   - 完了条件を1項目ずつ、根拠（PR・Issueコメント・コマンド出力）と対応付けて確認したか。根拠を示せない項目は未完了として扱う
   - 本文中の「別途検討」「別Issue」「対象外」「先送り」等の項目が、クローズ後も残る場所（Issue内の記録・親Issue・別Issue）に記録されているか。必要な引き継ぎが未記録なら移し先をユーザーに確認する。既存記録で追跡できるものに新たな管理先を機械的に追加しない
   - ステータスが現在の状態と一致しているか
   - 実施結果が必要な項目に記録されているか

2. **PR / Merge状態**
   - 対象PRが特定できるか
   - Merge済みか、未Mergeかを確認する
   - Mergeが必要なPRが未Mergeなら、クローズ可能な状態ではないことを明示する。調査のみなどPR不要のIssueは、その理由を記録し、PR作成を要求しない

3. **本番・実機確認**
   - 変更内容に必要な本番・実機確認の結果がIssue等に記録され、実施者・確認済み範囲・未確認範囲を区別できるか
   - 対象の版・配置も照合する。自動テスト、合成データ、ビルド成功、実画面確認を区別し、過去の成功記録を今回の再検証としない
   - ユーザー確認が必要な項目が残っていないか
   - 確認が不要なら、その理由を示す。本Skill自身は本番・実機確認そのものを代行しない

4. **ドキュメント**
   - README、変更に関連する`docs/`、Viewer変更時は`viewer/README.md`と、実装・仕様・運用手順の差異を確認したか。更新不要の場合も根拠があるか
   - 未対応なら、その対応を促し、既存ルールの範囲で必要な更新を進める

5. **関連Issue**
   - 派生・関連Issueがある場合、必要な相互リンクや引き継ぎが整理されているか

6. **Branch / stash / working tree**
   - 対象Issueのfeature branchがMerge済みか
   - Merge済みの対象ローカルbranchが残っていれば、既存ルールに従って`git branch -d`で整理する
   - リモートbranch削除はユーザー承認を得てから行う
   - `git stash list`とworking treeを確認し、対象Issueの未整理作業がないか確認する

7. **一時成果物・環境設定**
   - 対象Issueの作業記録、PR差分、使用したビルド・検証・配置手順を手掛かりに、その作業で作成・変更した一時成果物や環境設定の残存状況を確認する。Git管理外・ignore対象・リポジトリ外も含み、working treeがcleanなことだけで整理済みとしない
   - 該当する場合の例：モック、DerivedData等のビルド出力、描画画像・検証データ、仮配置・旧版Viewerやモックアプリ、残存プロセス、Launch Servicesのアプリ登録・Widget拡張登録、一時的な署名・配置・保存先設定。固定の削除一覧ではなく、そのIssueで使ったものを対象にする
   - 各対象を「整理済み／理由があって保持／対応待ち／判定不能」で整理し、根拠、保持理由または必要な対応を示す。容量が判断に役立つ場合は対象を限定して確認する。端末全体の走査や無関係なキャッシュ削除へ広げない
   - 現役の成果物・設定、復旧用の保管物、他Issueの作業を区別する。正式版と旧版の識別や登録情報の確認方法は対象プロジェクトの既存手順を参照する
   - 削除を一律に義務化しない。未整理のものはClose判断前にユーザーへ明示し、保持・後続対応・Closeへの影響を判断できるようにする。保持や先送りを勝手に承認済みとみなさない
   - 削除・登録解除・設定復元等は、影響範囲と既存の権限ルールを確認してから行う。調査できない対象は未確認として報告し、残存なしと断定しない

### blackboxでの対象の識別

Viewer関連では[Viewer利用ガイド](../../../viewer/README.md)と[開発メモ](../../../docs/project-development-viewer-notes.md)の「Widgetが旧版のまま表示される場合」「Dockのアプリアイコンが更新されない場合」を参照する。

- モック・画像がレビュー用にGitへ収録された成果物か、作業用の一時物かを区別する。Git管理内という理由だけで一律に削除・保持しない。
- ビルド・仮配置・正式配置の実パスと作成元を作業記録から照合する。稼働中の正式版、復旧用保管物、他Issueの成果物を旧版・不要物と混同しない。
- アプリのファイル、アプリ・拡張の登録、実行中のプロセスは別々に確認する。ファイル削除済みだけで登録整理済みとしない。登録先が正しいだけで新版が実行されているとせず、必要なら実行実体・開始時刻・読み込み済みファイル等を既存手順で照合する。
- プロセス名・bundle ID・PID・ファイル名の一致だけで対象や不要性を断定しない。
- 監視エンジンの配置・設定・データは[運用手順](../../../docs/operations.md)を参照する。runtime・設定・監視データの除去は別々に判断し、現行daemon・履歴DB・正常な運用設定を後片付けの対象と混同しない。

#22は後片付け確認の参考事例であり、当時の削除・復旧操作を再実施する指示ではない。macOS登録情報の一括初期化、他アプリのWidgetやDock設定の削除、共有ホストの再起動を定型手順にしない。監視開始・追加スキャン・DB変更・設定変更も、この確認だけを根拠に実行しない。

## 他Issueの作業を誤って触らないための必須ルール

対象Issueに関連するbranch / stash / working tree変更、一時成果物・環境設定を特定する際、Issue番号・branch名・PR・作業記録・作成元の手順等を照合しても対応関係を確実に判断できない場合は、対象とみなして操作してはならない。不明なものは「対象外候補」ではなく**「判定不能」**としてユーザーに提示し、確認を得るまで削除・pop・上書き等を行わない。

特に次を守る。

- 他Issueに紐づくと判断できるbranch・stash・変更は触らず、明示的に報告する
- 命名規則だけで関連性を断定しない
- 未コミット変更はbranchごとに分離されないため、working treeに複数Issueの変更が混在している可能性を考慮する
- 対応関係が不明なものへの操作は停止し、「判定不能」としてユーザー確認を待つ。独立して行える読み取り確認は続ける
- `git stash pop`、削除、上書き等の破壊的操作を、判定不能な状態で実行しない

## 操作境界

このSkillは操作権限を追加しない。以下は対象プロジェクトの指示と今回のユーザーの許可範囲内で適用し、既に得ている承認は引き継ぐ。必要な承認がまだなければ、具体的な対象・操作・影響を示して確認する。

既定ブランチ名・リモート名はプロジェクトから確認し、`main`・`origin`を決め打ちしない。Merge確認は最新の比較先とPR情報を照合し、古いローカル参照だけで判断しない。squash merge等でGitの到達可能性が一致しない場合も、強制削除へ切り替えず状態を報告する。

### 既存ルールの範囲で進めてよいもの

- `git status`
- `git stash list`
- `git branch --merged <既定ブランチ>`
- `git branch -r --merged <リモート>/<既定ブランチ>`
- 対象Issue / PR、一時成果物・環境設定の対象を限定した読み取り
- Issue本文の最新化（変更内容と編集権限を確認し、必要な承認を得た場合）
- Merge済みであることを確認した対象ローカルbranchの`git branch -d`

### ユーザー確認が必要なもの

- リモートbranchの削除
- 後片付けのために追加commit / push / PR作成が必要になる場合
- 削除・登録解除・設定復元等、既存ルールで承認が必要な環境への操作
- 対応関係が判定不能なbranch / stash / working tree変更、一時成果物・環境設定への操作

### 絶対に勝手に行わないもの

- `gh issue close`等によるIssueクローズ
- 他Issue・他セッションのbranch / stash / uncommitted変更の削除・pop・上書き
- Productionへの書き込み・deploy等、対象プロジェクトの指示で禁止・承認必須とされる操作
- チェック項目が全て完了したことをIssueクローズの承認とみなすこと

監視DB・実測生データ・ログ・秘密情報・端末固有パス・個人署名情報を公開しない。公開記録には一般化した名称や合成例を用いる。

## 完了時の報告

確認後は、少なくとも次を明示する。

- 確認したこと
- 対応したこと
- 未対応事項（一時成果物・環境設定の対応待ち、保持する対象と理由、未確認範囲を含む）
- 判定不能としてユーザー確認が必要な事項
- ユーザー承認が必要な操作
- Issueをクローズできる状態かどうかは、事実として整理する。ただしクローズ自体は行わない
- 「クローズ可能」と報告する場合は、完了条件ごとの根拠と残存対象の扱いを添える。機能受入完了だけで未整理事項なしとみなさない

本SkillではIssueをクローズしない。最終判断はユーザーに委ね、実際のClose操作は対象プロジェクトの開発フローとユーザーの明示的な指示に従う。
